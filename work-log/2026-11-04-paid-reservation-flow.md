# 유료 예약 결제와 환불 화면 연결

- 작업일: 2026-11-04
- 관련: 백엔드 기능 10·53·54·55·56·59·60·61·64, 계약은 백엔드 `docs/frontend/feature-10-deposit-payment.md`, `feature-53`~`56`, `feature-58`, `feature-60`, `feature-61`
- 기준: 프런트 `origin/dev@015f333`, 백엔드 `origin/dev@506872d`, 브랜치 `feat/p2-paid-flow`. 로컬 전용이며 push하지 않았다

## 배경과 목표

백엔드 결제 API는 dev에 있으나 프런트에 호출 코드가 없었다. 담당이 정해지지 않은 항목이라 황건하가 맡았다. 이번 범위는 유료 예약부터 취소·환불과 결제 내역 화면이다. 실제 Toss와 실제 매장 설정 연결은 범위가 아니다.

## 판단과 근거

- **유료 여부를 미리 판단하지 않는다.** 매장 응답에 예약금 정보가 없다. 기존처럼 `POST /reservations`를 보내고 `409 RESERVATION_PAYMENT_REQUIRED`일 때만 선점으로 넘어간다. 무료 매장 동작은 그대로다.
- **금액과 주문은 서버 값만 쓴다.** 인원수로 곱하거나 기본값을 넣지 않는다. 결제 전 환불 기준 표시는 고객 조회 API가 없어 넣지 않았다.
- **결과 불명을 실패로 보이지 않는다.** 응답 유실·시간 초과·`PAYMENT_RECONCILIATION_REQUIRED`는 "확인 중" 화면으로 보내고 새 결제를 막는다. 0초인데 `PENDING_PAYMENT`이면 승인 진행일 수 있어 만료로 단정하지 않는다.
- **화면 이탈로 선점을 해제하지 않는다.** 계약대로 5분 만료가 기준이고, "선점 취소"를 눌렀을 때만 해제한다.
- **환불 멱등키는 성공할 때까지 브라우저에 보관한다.** 결과 불명 뒤 새 키를 만들면 재시도가 거절되거나 이중 환불 위험이 있어 같은 키를 재사용한다.
- **점주 취소는 먼저 키 없이 보내고, `REFUND_NOT_COMPLETED`일 때 키와 함께 다시 보낸다.** 무료 예약의 기존 계약을 유지하기 위해서다.
- **Toss 키가 없으면 개발 서버에서만 결제창을 건너뛴다.** 로컬 전용 진행을 위한 것이며, 승인 여부는 여전히 서버가 판단한다. 배포 빌드에서는 오류로 막는다.
- **PG를 호출하는 요청은 시간 제한을 35초로 늘린다.** 기본 10초면 서버가 Toss를 기다리는 중에 프런트가 먼저 실패로 본다.

## 검증

로컬 실제 앱(백엔드 `bootRunLocalPaid`, 일회용 PostgreSQL 16, 가짜 Toss)과 브라우저에서 확인했다. 백엔드 쪽 시나리오 결과는 백엔드 `work-log/2026-11-04-local-paid-flow-verification.md`에 있다.

| 확인한 내용 | 방법 | 결과 |
| --- | --- | --- |
| 타입·빌드 | `npx tsc -b`, `npm run build` | 통과 |
| 린트 | `npm run lint` | 새 경고 없음. 기존 경고 2건(`StoreCard`, `Calendar`) |
| 예약 → 결제 → 확정 | 브라우저, 실제 앱 | 409 → 선점 201 → prepare 201 → 승인 → 예약 확정 화면 |
| 취소 → 환불 | 브라우저, 실제 앱 | 예상액 10,000원 표시, 취소 후 환불 완료, 결제 상세에 이력 표시 |
| 승인 응답 유실 | 브라우저, 가짜 Toss `drop` | 확인 중 화면, "다시 확인"으로 예약 확정 |
| 승인 거절 | 브라우저, 가짜 Toss `reject` | 재예약 안내 |
| 선점 만료 (진입 시) | 브라우저, DB 시각 조정 | 만료 안내와 다시 예약하기 |
| 선점 만료 (화면을 켜 둔 채 0초) | 브라우저, DB 시각 조정 | 첫 확인에서 멈춤 발견. 수정 후 만료 안내로 자동 전환 |
| 선점 취소 | 브라우저, 실제 앱 | `CANCELLED`, 매장 화면으로 이동 |
| 점주 유료 취소 | 브라우저, 실제 앱 | 409 뒤 키와 함께 재요청 200, 전액 환불 |
| 목 모드 | 개발 서버 기본값에서 API 호출 | 유료 매장 흐름이 실제와 같은 형태로 동작 |

브라우저에서 발견해 고친 것:

- 방금 만든 예약을 바로 취소해도 "예약이 확정됐어요"가 남던 문제.
- 화면을 켜 둔 채 0초가 되면 "진행 중인 결제가 있을 수 있어요"에서 멈추던 문제. 남은 초가 내림값이라 실제 만료 1초 전에 한 번만 재조회했다. 0초인 결제 대기 선점은 결론이 날 때까지 3초마다 다시 조회한다.

실제 Toss 결제창은 열어 보지 않았다. 클라이언트 키를 넣은 경로는 타입 검사까지만 확인했다. CI·배포도 확인하지 않았다.

## 남은 점과 후속 작업

- 실제 Toss 결제창과 키 짝 확인. `test_gck`가 이 결제창 방식에 맞는지 확인되지 않았다
- 기능33 머지 후 실제 매장 설정으로 재검증. 결제 전 금액·환불 기준 표시도 그때 판단한다
- `refundRequired` 결제는 안내만 한다. 백엔드 `POST /payments/{id}/cancel`이 확정 예약만 받아 고객이 환불을 요청할 경로가 없다
- 돈만 환불하는 `POST /payments/{id}/cancel` 화면은 만들지 않았다. 예약을 유지한 채 환불받는 고객 시나리오가 정해지지 않았다

## 2026-11-05 선점·결제 후속

사용자가 백엔드 기능53~56의 후속 범위를 프런트 저장소까지 확대했고 Toss 인증 보류는 유지했다. 기존 `feat/p2-paid-flow@86c746e89bbd01e61dfbe5dc6c1cc561d99ab669`의 다섯 로컬 커밋과 화면을 재사용했다. 시작 상태는 clean이며 기존 커밋은 복구 bundle로 보존했다. 기본 프런트 체크아웃·다른 작업트리는 수정하지 않았다.

### 문제와 보완

- 캐시된 READY 주문만으로 결제창을 열면 SDK 로딩 중 만료되거나 다른 탭에서 시작한 승인을 놓칠 수 있었다. SDK가 준비된 뒤 서버 prepare를 다시 호출한다. 유효한 같은 READY와 양수 남은 시간이 있을 때만 창을 열며 최초 주문·금액·기한을 유지한다. 중복 클릭과 준비 재조회·취소 중 새 시작도 막는다.
- confirm의 코드가 있는 HTTP500/502/503을 실패 화면으로 보내던 경로를 재현했다. 서버 오류·408·429와 응답 유실은 결과 불명으로 표시하며 해제하지 않는다. 실제 서버가 반환한 FAILED/CANCELED만 반환 안내로 연결한다. 서버가 확인하지 않은 재고 보호를 화면에서 단정하지 않는다.
- 선점 취소가 승인 보호 때문에409로 거절됐는데도 오래된 결제 버튼이 남던 문제를 재현했다. 선점·prepare를 재조회해 기존 결제 결과 확인으로 연결한다.
- 기존 결제를 첫50건에서만 찾던 경로를 페이지 끝까지 조회하게 바꿨다.
- 개발 서버의 키 누락을 합성 키 승인 이동으로 처리하던 동작을 제거했다. MSW 또는 명시적 개발용 `VITE_TOSS_SIMULATION=true`만 fake 경로를 사용하며 배포에서는 해당 플래그가 꺼진다. 비밀 설정 파일은 읽거나 변경하지 않았다.

### 로컬 검증

- Node26.12.0/npm11.20.0. 자동 검사에는 Vitest5.1.0·Testing Library·jsdom을 추가했다. 최초 재현 실행은17개 중9실패/8통과였고, 보호된 취소 거절의 추가 재현은22개 중1실패/21통과였다. 각 최초 실패 로그를 보존했다. 최종 단일 실행 결과는22개 통과, 실패·건너뜀0이다. 이전 실행 건수를 합산하지 않는다.
- `npm run lint`, `npm run build` 통과. 새 린트 경고는 없고 기존 `Calendar`·`StoreCard`의2건은 유지한다. 빌드와 타입 검사를 화면 검증으로 대신하지 않는다.
- Playwright Chromium의390×844 화면에서 아래7개 시나리오가 통과했다. 가로 넘침이 없음을 확인하고 화면을 렌더링해 검토했다. 사용자 브라우저 제어 경로(Aside의 stale ref, Codex 컴퓨터 유즈 연결/시간 초과)는 실패했고, 별도 Playwright 테스트 브라우저로 전환했다.

백엔드는 이 후속에서 운영 코드·마이그레이션을 변경하지 않았다. 새 일회용 PostgreSQL16(`127.0.0.1:59541`, `ct_p2_hold_test`, tmpfs)에서31 SQL(V32까지)을 적용하고 백엔드 관련8클래스166개가 실패·오류·건너뜀0으로 통과했다. 이는 이전 hosted CI915개와 별도 실행이다. 브라우저는 MSW를 끄고 실제 앱 `127.0.0.1:60461`에 연결했으며 서버 PG 구현만 기존 fake를 재사용했다. 실제 PG base URL은 loopback의 닫힌 포트로 설정했고 브라우저에서도 외부 호스트를 차단했다.

이번 Clock 전진은 실제5분 대기 검증이 아니다. 실제5분 만료·재선점의 과거 근거는 백엔드 PR #249의 `work-log/2026-11-05-p2-app-toss-verification.md`에 보존했다. 502 치환은 로컬 응답 유실 모사이며 실제 통신 장애·실제 Toss·앱 재시작 검증이 아니다.

전체 로그·JUnit·브라우저 검증기·결과 JSON·모바일 캡처는 백엔드 공통 Git 디렉터리의 `orca-artifacts/p2-hold-integration-20261105-av4q6ovb`에 보존한다. 실제 기능33 미연결이라는 위11월4일의 후속 조건은 이번 로컬 검증에서 해소됐다. 실제 Toss 인증·정상 양수 승인/환불·재시작 복구·CI·배포는 완료하지 않았다. 외부 게시·머지는 이 기록의 로컬 구현/검증과 별도다.

검증 후 정리 시 최종 상태 조회가500으로 실패했다. 전용 컨테이너는 이미 없고 원래 DB 포트도 닫혀 있어 DB dump는 만들지 못했다. 사라진 원인은 확인하지 않았다. 그 전에 통과한 JUnit·브라우저 결과·상태 확인·캡처는 보존했고 남아 있던 검증용 앱·프런트 프로세스와 두 포트의 종료를 확인했다. 이 정리 실패를 테스트 통과로 세지 않으며 재개 시 새 전용 DB가 필요하다.
