# 매장 검색·예약·영업시간·웨이팅의 실제 API 연동 수정

- 작업일: 2026-10-31
- 기준: 프런트 `dev`의 `0127d7ef9d3981a24860dd29f0c83160a60df5b1`, 백엔드 `dev`의 `342f86e8fe3ab9e1874806f1ffd7f85a787bfaa6`
- 관련 명세: [조건별 검색](https://app.notion.com/p/3d548d76fa328167bcfadfb92c124e48), [예약 가능 시간·잔여 테이블](https://app.notion.com/p/3d548d76fa32817389b8dee3a96d5350), [영업시간 관리](https://app.notion.com/p/3d548d76fa3281bfa916f1cf77badc39)

## 배경과 승인한 범위

목 API와 실제 백엔드의 목록 형식, 공공 매장 예약 지원 여부, 심야 영업과 브레이크타임, 재고 충돌 처리의 차이를 맞춘다. 기존 프런트 폴더의 `fix/api-integration` 브랜치에서 작업하고 기존 로컬 `dev` 참조는 보존했다. 백엔드는 최신 `dev` 기준 별도 작업 공간을 사용했다.

| 항목 | 승인한 동작과 변경 |
| --- | --- |
| 목록 | `stores/page/size/hasNext` 응답을 읽고 처음 10개와 `더 보기`로 다음 10개를 추가한다. 조건 변경 시 첫 페이지부터 조회한다. |
| 이름 검색 | 입력을 멈춘 뒤 300ms 후 `keyword`를 서버에 보낸다. 현재 페이지 안의 이름만 필터링하지 않는다. |
| 검색 → 예약 | 날짜·누른 시간·인원을 상세 URL로 전달하고 예약 시트에 채운다. 가용성 응답을 확인한 뒤 다음 단계로 진행한다. |
| 공공 매장 | 상세 응답의 `reservationEnabled`가 `false`이면 예약 버튼을 비활성화하고 사유를 표시한다. 가용성 조회·예약 시트·직접 예약 경로도 차단한다. |
| 브레이크타임 | 각 요일의 사용 여부와 시작·종료를 개별 편집한다. 다른 요일의 값을 공통 값으로 덮어쓰지 않는다. 자정을 넘는 시각도 영업 구간 기준으로 검증한다. |
| 심야·휴무 | 요일만 보고 날짜를 막지 않는다. 서버가 반환하는 전날 심야 슬롯을 표시하고 빈 날짜에는 `예약 가능한 시간이 없어요`를 안내한다. |
| 재고 충돌 | 예약 생성의 `HTTP_409`이면 선택한 시간을 지우고 날짜·인원을 유지한 채 시간 선택으로 복귀한다. 가용성을 재조회하며 자동 재전송하지 않는다. |
| 수량 | `availableTableCount`는 좌석 수가 아닌 `N테이블`로 표시한다. |

목 핸들러도 페이지 객체·검색어, 공공 매장 제한, 심야 영업·브레이크타임, 재고 충돌 코드에 맞췄다. TanStack Query·기존 예약 폼 스토어·공통 UI를 재사용했고 의존성·잠금 파일과 환경 파일은 변경하지 않았다.

노션 검색 문서의 2026-10-29 기록은 `keyword`를 후속 항목으로 적지만, 이번 기준 백엔드에는 검색어 DTO·쿼리가 있다. 요일별 브레이크 편집은 현재 API가 지원하는 요일별 한 구간 범위다. 노션에 있는 특정일 예외·여러 영업 구간을 이번에 구현했다고 간주하지 않는다.

## 검증

- Node.js 26.12.0 / npm 11.20.0, 기존 설치 의존성에서 `npm run lint`, `npm run build` 성공. 프런트 자동 테스트 실행기는 새로 도입하지 않았다.
- 실제 연동: 새 PostgreSQL 16 컨테이너·전용 앱 DB, 백엔드 18080·프런트 15173, `VITE_API_MOCKING=false`. 별도 브라우저 컨텍스트에서 API 응답이 서비스 워커를 통하지 않음을 확인했다.
- 목 API 검증: 별도 브라우저 컨텍스트에서 MSW를 켜고 목록·검색·공공 매장·심야 브레이크 경계를 확인했다. 실제 서버 검증과 구분한다.
- 화면 확인: 375px 폭에서 검색 시간 버튼의 `N테이블` 표시와 요일별 영업시간·브레이크 편집을 확인했다. 문서 전체의 가로 넘침은 없었다.

| 실제 서버 시나리오 | 확인 결과 |
| --- | --- |
| 홈·검색 목록 | 합성 매장 16개에서 최초 10개 → 더 보기 후 16개 |
| 서버 이름 검색 | 첫 페이지 밖의 매장도 검색됨. 변경 요청의 `page=0` 확인 |
| 공공 매장 | 지원 여부 `false`, 비활성 버튼·사유, 가용성 요청 없음, 직접 예약 차단 |
| 요일별 시간 저장 | 월 15–16시·화 16–17시 브레이크 보존, 수 18–익일 04시와 브레이크 23–익일 01시 저장 200 |
| 심야 날짜 | 금요일 밤 영업의 토요일 00:30 선택 가능. 일요일 빈 시간 안내 |
| 예약 완료 | 검색의 날짜·19:30·4명 유지, 실제 생성 201·상세 이동 |
| 마지막 테이블 충돌 | 같은 요청의 경쟁 예약 201 뒤 화면 요청 409. 날짜·4명 유지, 시간 해제·재조회, 화면 POST 1회 |

목 API에서는 최초 10개·다음 페이지·목록 밖 이름 검색, 공공 상세 `false`·가용성 404, 금 18–익일 04시·브레이크 23–익일 01시 저장을 확인했다. 토 01:00 슬롯 포함·00:30 제외, 금 22:30 시작 후 브레이크와 이용시간이 겹치는 슬롯 제외도 통과했다.

백엔드 전체 빌드는 71클래스 786개, 실패·오류·건너뜀 0이다. 이는 로컬 검사이며 CI·배포·실제 결제 연동 결과가 아니다. 합성 데이터만 사용했고 기존 DB·컨테이너를 변경하지 않았다.

## 웨이팅 추가 승인 범위와 검증

추가 웨이팅 연동은 처음에 신청 201 → 점주 호출 → 고객 수락 200 이후 완료 표시 단계에서 실패했다. 서버는 `CALLED`를 유지하며 방문 의사·응답 시각을 기록하지만 화면과 목 API는 `CONFIRMED` 전환을 가정했다. [호출 응답 명세](https://app.notion.com/p/3d548d76fa3281358b3aeee972d44d59)도 호출 상태 유지를 요구한다. 이 추가 범위는 별도로 승인을 받은 뒤 수정했다.

- 고객 상세 조회에 추가한 `respondedAt`·`arrivalIntent`로 수락 완료를 표시한다. 수락 버튼을 숨기고 새로고침 후에도 서버 조회로 복구한다. 기존 `CONFIRMED` 데이터의 표시 호환은 보존한다.
- 수락 완료 문구는 승인한 `방문 의사를 전달했어요. 제한시간 안에 입장해주세요`를 사용한다. 성공 알림도 방문 의사 전달로 표시해 실제 도착·착석과 구분한다.
- 점주 목록의 기존 응답 필드로 `방문 예정`과 응답 시각을 표시한다. 실제 상태는 `CALLED`이며 착석은 점주가 별도로 처리한다.
- 목 API도 `CALLED` 유지·최초 응답 시각 재사용·재호출 시 응답 초기화와 호출 횟수를 맞췄다. 호출 전·종료 후 조회 정보는 실제 서버와 같이 `null`이다.
- 수정 후 기존 7개와 웨이팅 1개, 실제 서버 브라우저 시나리오 총 8개가 통과했다. 수락 후 새로고침, 반복 수락의 응답 시각·기한 불변, 재호출 후 응답 초기화, 다시 수락 후 점주 착석·최종 `SEATED`를 확인했다.
- 별도 MSW 컨텍스트에서 HTTP·점주 SSE로 응답 필드, 반복 수락의 추가 알림 없음, 소유권 404, 재호출·착석·종료 정보 숨김을 확인했다. 최종 lint·build도 통과했다.

## 재검증에서 발견한 UI 경계와 후속 수정 — 2026-10-31

기존 성공 흐름을 다시 실행하는 것과 별도로 실패·선택 표시 경계를 검사해 다음 세 가지를 재현했다. 모두 수정 방향을 승인받고 보완했다.

| 수정 전 재현 | 승인한 변경 |
| --- | --- |
| 다음 페이지에 503을 반환하면 검색의 기존 매장 10개도 사라짐 | 홈·검색 모두 기존 목록을 유지하고 하단에 오류·재시도 표시 |
| 11월 1일 검색으로 들어가도 달력은 10월, 선택 날짜 셀 없음 | 전달된 날짜가 바뀌면 해당 달로 이동. 사용자의 수동 월 탐색은 유지 |
| 검색은 20명까지 받지만 예약 시트 옵션은 1~8명뿐이어서 9명을 선택·재선택할 수 없음 | 예약 폼도 기존 검색과 같은 1~20명 옵션 사용 |

`Calendar`의 전달값 변경 처리, 예약 폼의 기본 인원 범위, 홈·검색의 다음 페이지 오류 분기만 보완했다. 1~20명은 화면 입력 옵션이며 모든 매장의 수용 가능 인원을 뜻하지 않는다. 실제 가용성과 한 테이블의 수용 여부는 기존 서버 조회·생성 검사를 따른다. 테이블 합치기나 API·DB 계약을 추가하지 않았다.

| 후속 검증 | 결과 |
| --- | --- |
| 홈·검색의 다음 페이지 503 → 재시도 | 각각 기존 10개 유지, 정상 응답으로 재시도 후 16개 |
| 홈·검색의 최초 조회 503 → 재시도 | 전체 오류·재시도 표시 유지, 재시도 후 최초 10개 |
| 검색 날짜 전달 | 11월 1일 전달 시 11월 달력·1일 선택 표시. 12월 수동 탐색 유지, 11월 2일로 바꾼 뒤 시트를 닫았다 열어도 2일 유지 |
| 인원 전달·재선택 | 9명 선택 표시와 20개 옵션 확인. 9→8→20→9명 변경 가능. 격리 앱 DB의 합성 테이블로 실제 가용성 확인 후 테스트 테이블 비활성화 |
| 이름 검색 지연 | 입력 시작 기준 325ms 후 검색 요청 1회 |
| 전체 실제 연동 | 수정 후 기존 8개 브라우저 시나리오 재통과, 브라우저 오류 0·서비스 워커 응답 없음 |
| 정적 검사 | 수정 후 `npm run lint`, `npm run build` 통과 |
| 백엔드 재검증 | 전용 DB의 `./gradlew build --rerun-tasks --no-daemon --console=plain`, 71클래스 786개 재실행·실패/오류/건너뜀 0 |

다음 페이지 503은 브라우저에서 의도적으로 주입한 장애이며, 정상·재시도 요청은 실제 백엔드를 사용했다. 목 API 검증은 이 재검증에서도 별도 컨텍스트로 통과했다. 전체 검증은 기존 사용자 데이터와 분리한 테스트 DB에서 진행했다.
